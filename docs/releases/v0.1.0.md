mssql-readonly-mcp is an MCP server that lets an AI assistant read one on-premises SQL Server database. Its SQL tool accepts only text that passes an allowlist for one plain SELECT, and it will not start with a login that fails its permission check ([what that check covers and what it does not](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/login-check.md#what-check-login-refuses)). It keeps a tamper-evident record (a hash-chained audit file) of every question asked. This is the first release.

| `SHA256SUMS` | SHA-256 of the six files above |

Each build is self-contained: the .NET runtime is included (not trimmed, not Native AOT). The program is `mssql-readonly-mcp` (`mssql-readonly-mcp.exe` on Windows). On Linux the README lists the ICU libraries (for example the `libicu` package) as a prerequisite: the server turns globalization on because Microsoft.Data.SqlClient needs it ([Prerequisites](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/README.md#1-prerequisites)). No code signing: the Windows executable is not Authenticode-signed, the macOS executable is not notarized, and the bundles are not signed with `mcpb sign`. No builds for other platforms ([details](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/releasing.md#not-done-by-this-workflow)).

When these notes were written, the packaging had been tried only with local builds on a Windows machine with the .NET SDK installed. Not yet shown then ([details](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/releasing.md#not-yet-verified)): starting the Linux build on Linux and the macOS build on a Mac, including whether Gatekeeper starts an executable that is not notarized; starting a build on a machine with no .NET installed at all; that the executable bit is kept in the `.tar.gz` archives and `.mcpb` bundles; installing a `.mcpb` bundle in any MCPB host.

The bundles are packed with the MCPB CLI pinned in `packaging/mcpb/package-lock.json`; their attestation shows that the release workflow built them, not that this tool left the server files unchanged. `packaging/mcpb/package.json` overrides two packages under the CLI, so the CLI runs with dependency versions its author did not pin: `tmp` 0.2.7 where its tree asks for 0.0.33, and `zod` 4.6.7 where it asks for 3.x, because no version in the ranges it asks for has the fix for their known vulnerabilities. With them, `npm audit --package-lock-only` on 2026-11-13 reported 0 vulnerabilities, and bundles packed on Windows with the old and the new lock file held the same files with the same content ([details](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/security-testing.md#dependency-alerts)).

```powershell
(Get-FileHash .\mssql-readonly-mcp-0.1.0-win-x64.zip -Algorithm SHA256).Hash.ToLowerInvariant()
```

The release workflow attests every file in `SHA256SUMS` (build provenance). The check below is meant for that attestation; when these notes were written, it had not been run against a real release. ```

## What it does

| Promise, in short | Full text |
| --- | --- |
| A write or DDL statement is refused before it reaches SQL Server, by an allowlist over the ScriptDom syntax tree, not a keyword filter. | [Writes refused before SQL Server](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/promises.md#writes-refused-before-sql-server) |
| In every case tested, SQL Server ran the allowed text or refused it before running. | [Allowed text on a real SQL Server](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/promises.md#allowed-text-on-a-real-sql-server) |
| The server refuses to start with a login that fails its permission check: exit code 3, no override. | [Login check at startup](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/promises.md#login-check-at-startup) |
| No call returns data before its hash-chained audit line is written. If the line cannot be written, the query has still run and the call returns an error and no data. | [Audit line before data](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/promises.md#audit-line-before-data) |
| Results are capped by rows, characters and time. | [Result caps](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/promises.md#result-caps) |
| A query waits a bounded time for locks and loses deadlocks against default-priority sessions. Its own shared locks can still make a writer wait, until the call ends, and for a call ended as `Timeout` or `Cancelled` at its cutoff until its clean-up at SQL Server ends, which can be after the answer, and on a slow link a `Timeout` can leave them longer, with its session ([U-1R](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/SECURITY.md#known-limits)). | [Lock timeout and deadlock priority](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/promises.md#lock-timeout-and-deadlock-priority) |

Three tools: `list_tables`, `describe_table` and `run_query`. Only `run_query` takes SQL, and that SQL goes through the gate ([Tools](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/reference.md#tools)).

## Tested on

SQL Server 2019, 2022 and 2025, as Linux container images pinned by exact tag: `mcr.microsoft.com/mssql/server:2019-CU32-GDR13-ubuntu-20.04`, `2022-CU27-ubuntu-22.04` and `2025-CU9-GDR1-ubuntu-22.04`. Other versions and Windows installations were not tested. Test counts: Gate 367, Audit 55, Integration 259 on each of the three images. One integration test, `Truncated_result_whose_cancel_is_held_until_the_network_works_again_holds_its_locks_until_then_only`, is not stable: it failed once in the last full run, on the 2022 image (258 of 259), and in 4 of 19 runs on that image on the code of this release and of the commit before it; that it has the same cause as U-1R below is reasoned, not proven, and it can fail in a CI run or a local run ([Building and testing](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/building-and-testing.md)). CI runs on every push and pull request: the build and unit tests, then, when they pass, the integration tests on each of the three images.

## What it does not solve, and known limits

Read [What it does not solve](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/README.md#what-it-does-not-solve) before you install it. Five limits to know first:

| Limit | Where |
| --- | --- |
| The rows the assistant reads leave your building. They go to the AI vendor that runs the model, with the table and column names and any SQL Server error text. Read-only does not change that. | [README](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/README.md#what-it-does-not-solve) |
| The login check runs once, at start. Rights granted afterwards to the login, a role it is in or `public` are not seen until the server restarts. | [What `check-login` refuses](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/login-check.md#what-check-login-refuses) |
| A call that has not ended 0.5 s after its time limit, its clean-up included, is answered as `Timeout` with no data (`Cancelled`, with no answer, if the client cancelled it first); in attack test run 4 every such `Timeout` of a single call came at most 0.56 s past the limit. A call that ends before its cutoff keeps its own outcome, so an `ok` answer with data can arrive up to 0.5 s after the limit, or later when the answer itself is delayed. Many calls frozen at once in the middle of a row delay the answers of every call, healthy ones too: in attack test run 4, at a limit of 5 s with 60 or 120 such calls, the median answer came after 8.2 to 30.2 s (run 5, with 60: 10.2 to 12.1 s). The clean-up of a call answered at its cutoff goes on at SQL Server after the answer, and the session keeps its read transaction and locks until it ends (on a broken connection, once the client's close reaches SQL Server); on a link throttled to 5 KB/s, attack test run 5 found 8 of 27 single `Timeout` calls whose client never closed the connection, so the session kept its read transaction and a lock to the end of the observation, and 21 of 450 calls repeated 50 in a row whose session still held them 45 s after the release (U-1R). A client that calls again after each `Timeout` can add one more such session each time, when that call's clean-up has not ended at its cutoff; the server sets no limit of its own on them (attack test, 50 calls in a row on a frozen link: the sessions grew by one per call with the default pool and with `Pooling=false`, and stopped at 5 with `Max Pool Size=5`; run 5, on `a38fd06`, the same, except that with `Max Pool Size=5` they reached 12 on SQL Server 2022). The server does not limit how many calls run at once. | [SECURITY.md, "Known limits"](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/SECURITY.md#known-limits) |
| Requests the MCP SDK or its stdio transport rejects or drops before the server sees them run no tool and get no audit line. | [Requests with no audit line](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/audit-log.md#requests-with-no-audit-line) |
| The server sets `ApplicationIntent=ReadOnly`, so behind an availability group listener with read-only routing the login check and later calls could reach different replicas; this is not tested. A grant to a Windows or Microsoft Entra group is asked by the login check, but that branch was not measured. | [What `check-login` refuses](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/login-check.md#what-check-login-refuses) |

More limits are in SECURITY.md "Known limits" (linked above), [What the reader sees at server level](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/reference.md#what-the-reader-sees-at-server-level) and [the audit log](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/audit-log.md).

## Start

Follow the [five-minute start](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/README.md#five-minute-start) in the README. It is written for a build from source and starts the server as `dotnet <path to mssql-readonly-mcp.dll>`; in a downloaded folder the program is `mssql-readonly-mcp` (`mssql-readonly-mcp.exe` on Windows), started directly without `dotnet`, with the same commands ([Commands and exit codes](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.0/docs/reference.md#commands-and-exit-codes)).
