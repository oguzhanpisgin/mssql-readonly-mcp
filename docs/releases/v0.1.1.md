mssql-readonly-mcp is an MCP server that lets an AI assistant read one on-premises SQL Server database. Its SQL tool accepts only text that passes an allowlist for one plain SELECT, and it will not start with a login that fails its permission check ([what that check covers and what it does not](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.1/docs/login-check.md#what-check-login-refuses)). It keeps a tamper-evident record (a hash-chained audit file) of every question asked. This release closes, best effort, a session that a `Timeout` on a slow link could leave open in v0.1.0 (U-1R; retested on SQL Server 2022 on Windows only), adds an icon to the bundles and corrects the docs. The gate, the login check, the tools and the audit format are unchanged.

## Changes

- **U-1R: a `Timeout` on a slow link could leave its session open in v0.1.0.** In attack test run 5, on a link throttled to 5 KB/s, 8 of 27 single calls (limit 3 s) and 21 of 450 calls repeated 50 in a row (limit 2 s), each answered `Timeout`, left the reader's session at SQL Server with an open read transaction and a lock (no data leak, no audit gap). The cause, diagnosed after v0.1.0 with a build that logs the client library's state (SQL Server 2022 image, on Windows): the client library's command timeout fires in the middle of a row while the server's reader close drains the throttled result; the library breaks the connection, and its parser becomes `Closed`, but the same read goes on parsing, reads row data as a token and breaks the connection a second time, which leaves the parser `Broken`. v0.1.0 closed only a connection whose parser was `Closed`, so it left this one open. The server now also closes a connection whose parser is `Broken`, when the client library has doomed it, the call's own `SqlConnection` is closed and no other `SqlConnection` holds it, with the earlier checks (the network handle is still there, no network callback is pending). The close is still best effort, and it fails closed: when an internal member of the client library that it reads is missing, it closes nothing, and the Gate tests fail. New unit tests (`LeftOpenConnectionsDecisionTests`) check each condition without SQL Server.
- **Bundle icon.** The `.mcpb` bundles carry the project logo as their icon (`icon.png`); the v0.1.0 bundles had none. A win-x64 bundle built locally with the release script held the icon unchanged, and its manifest named it; a bundle built by the release workflow was not checked, nor how a host shows the icon.
- **README images.** The banner and the two diagrams are one self-contained dark card each, instead of a light and a dark variant: with GitHub's theme set to follow the system, a dark GitHub theme on a light system showed the light images on a dark page.
- **Registry file.** `server.json` at the repository root is the entry published to the official MCP registry; [Releasing](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.1/docs/releasing.md) has the step that updates it after a release. At this tag it still names v0.1.0; it is updated after this release is published.
- **Docs.** The sentences written before the v0.1.0 release now say what was checked after it; stale sentences found in a full audit are corrected; the issue forms carry their labels and ask for the release version; the U-1R sentences in the README, SECURITY.md and the docs describe the fix.

## Measured for the U-1R fix

Retest on 2026-11-13, on Windows, against the SQL Server 2022 image (`2022-CU27-ubuntu-22.04`), one call per run in a new server process: a `Timeout` on a link throttled to 5 KB/s from SQL Server to the client, limit 3 s, the throttle released 10 s after the limit. In 100 of 100 runs the call was answered `Timeout` (3.5 to 3.8 s after it started), the client closed the connection 6.0 to 6.4 s after the start, while the link was still throttled, the call's session was gone 6.0 to 6.6 s after the start, the next call worked and the server exited with code 0; no run left the session. A diagnostic build of the same code, which also logs the client library's state and the close decision (this instrumentation can change timing), 25 runs of the same case: none left the session; the parser was `Broken` in 2 of them (in both the connection was doomed and had no owner) and `Closed` in 23, and the server closed the connection in all 25. In the diagnosis, the same case with the throttle held 60 s, on the code before the fix, left the session in 5 of 12 runs. Unit tests on Windows on 2026-11-13: Gate 416, Audit 90, all passed. The code of this release differs from the retested build only in source comments.

Not shown for the fix: SQL Server 2019 and 2025 in the throttled case; the 50 calls in a row of run 5; a link throttled for 60 s as in run 5; a real slow network (the retest throttles a local link); Linux and macOS. The attack tests were not run again ([Security testing](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.1/docs/security-testing.md#findings), U-1R).

## Check a download

Compare the file's SHA-256 with its line in `SHA256SUMS` (on Linux: `sha256sum --check --ignore-missing SHA256SUMS` in the download folder):

```powershell
(Get-FileHash .\mssql-readonly-mcp-0.1.1-win-x64.zip -Algorithm SHA256).Hash.ToLowerInvariant()
```

The release workflow attests every file in `SHA256SUMS` (build provenance). The check needs the GitHub CLI ([details](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.1/docs/releasing.md#how-a-user-checks-a-download)):

```powershell
gh attestation verify .\mssql-readonly-mcp-0.1.1-win-x64.zip --repo oguzhanpisgin/mssql-readonly-mcp
```

## Tested on

SQL Server 2019, 2022 and 2025, as Linux container images pinned by exact tag: `mcr.microsoft.com/mssql/server:2019-CU32-GDR13-ubuntu-20.04`, `2022-CU27-ubuntu-22.04` and `2025-CU9-GDR1-ubuntu-22.04`. Other versions and Windows installations were not tested. In the last full run before this release (2026-11-13, on Windows, one run per image) all tests passed: Gate 416, Audit 90, and Integration 259 of 259 on each of the three images ([Building and testing](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.1/docs/building-and-testing.md)). One integration test, `Truncated_result_whose_cancel_is_held_until_the_network_works_again_holds_its_locks_until_then_only`, is still not stable: it passed in those three runs, which does not show it stable, and failed in 4 of 19 runs on the 2022 image, on Windows, on earlier code; no failure message was captured then, so the cause of those failures is not known. The failures whose message was captured after v0.1.0 (one in 40 local runs on the 2022 image, one CI run on the 2019 image) had a cause other than U-1R: the request had ended while the cancel was held; in the local one, SQL Server ended it on its own because the whole result fit into the network buffers between SQL Server and the test's proxy. The fix does not change that; it can fail in a CI run or a local run. CI runs on every push and pull request: the build and unit tests, then, when they pass, the integration tests on each of the three images.

## What it does not solve, and known limits

Unchanged from v0.1.0 except U-1R above. Read [What it does not solve](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.1/README.md#what-it-does-not-solve) and [SECURITY.md, "Known limits"](https://github.com/oguzhanpisgin/mssql-readonly-mcp/blob/v0.1.1/SECURITY.md#known-limits) before you install it. The rows the assistant reads still go to the AI vendor that runs the model; read-only does not change that.
